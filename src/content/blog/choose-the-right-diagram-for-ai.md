**Vibe Coding 的时候，你还在每次都让 AI 生成“架构图”或“结构图”吗？**

接手一个项目，先来一张架构图。准备加个功能，再来一张结构图。遇到 Bug，把需求改成“画一张更详细的架构图”。

AI 很配合：前端、后端、数据库，几个方框，几条箭头。图越来越大，但你想知道的事可能还是没讲清：上传为什么卡住？哪个服务必须先启动？这次改动到底会影响谁？

“架构图”三个字留给 AI 的解释空间太大了。它可能给你一张技术栈清单，也可能给你一张部署示意，或者把目录、模块、业务步骤全塞进去。

想让图有用，先补上一句话：**我希望看完这张图之后，能够做出什么判断？**

## 先用四个问题区分四类图

| 你想弄清什么 | 优先选择 | 图里重点表达的关系 |
| --- | --- | --- |
| 系统由哪些部分组成，下面还包含什么？ | 结构图 | 包含、归属、层级 |
| 各部分分别负责什么，如何协作？ | 架构图 | 职责、边界、依赖与交互 |
| 运行时谁连着谁，通过什么连接？ | 拓扑图 | 物理或逻辑连接；按需补充部署位置 |
| 一件事从开始到结束，经历哪些步骤和分支？ | 流程图 | 先后、条件、循环、异常出口 |

这里先说明一个容易误会的地方：**这不是四个严格互斥的标准分类。**

“架构图”是一个比较宽的说法，结构、部署、动态交互都可以成为架构文档的一部分。C4 模型就同时提供静态结构图，以及动态、部署等配套视图。[C4 官方图示说明](https://c4model.com/diagrams)

“结构图”在日常沟通里也很宽泛，可能指功能结构、模块结构、目录结构，甚至数据结构。本文先把它收窄为“组成与层级视图”，便于选择。

所以下面的区分，是一套与 AI 沟通时的实用方法。图名可以有重叠，但你要表达的关系得明确。

## 同一个 AI 知识库，换四个视角看

假设我们准备做一个小型 AI 知识库：用户上传文档，后台解析并建立检索内容，之后可以提问，让模型根据检索到的片段回答。

为了方便对照，下面四张图都基于同一个**假设方案**：Web 页面调用 API；API 和后台 Worker 共用 PostgreSQL；Worker 从任务表领取解析任务；API 检索文档片段后调用外部模型。本例暂用数据库的全文检索，不引入独立向量库或消息队列。

这些只是教学设定，不是对任何现有项目的扫描结果，也不代表所有知识库都应该这样实现。

### 结构图：先把“有哪些”拆清楚

如果你刚有一个产品想法，想确认功能有没有漏，可以先画功能结构图。

![AI 知识库的功能结构图：文档管理、知识问答、历史记录三个分支，各自包含对应功能。](/images/blog/choose-the-right-diagram-for-ai/structure.svg)

这里每条连线都表示“包含”。文档管理包含上传和删除，知识问答包含检索和生成回答。

它适合帮助你拆需求、定范围、组织模块。如果你的目标是熟悉代码，则应该进一步指定“画代码模块结构图”或“输出目录树，并说明各目录职责”。

**功能树不能直接证明运行时的调用关系。** “文档管理”和“知识问答”并排摆着，也不代表它们互不依赖。

可以这样问 AI：

```text
请根据下面的产品需求，画一张功能结构图，帮助我确认 MVP 范围。
按“产品 → 功能模块 → 子功能”展开，最多三层。
连线只表示包含关系，不表示调用顺序。
把需求明确提到的功能与建议补充的功能分开列出。
不要把技术选型、服务器或数据库当成功能节点。
```

### 架构图：讲清“谁负责什么，怎么配合”

功能范围确定后，你开始考虑实现：上传由谁接收？耗时解析放在哪里？谁有权限调用模型？

这时画架构图更合适。

![AI 知识库的应用架构图：Web 页面调用 API，API 写入任务并检索数据库、调用外部模型；Worker 从数据库领取任务并写入解析结果。](/images/blog/choose-the-right-diagram-for-ai/architecture.svg)

这张图想表达的是职责分配：

- **Web 页面**负责交互和状态展示。
- **API**负责请求入口、任务创建、检索和回答生成。
- **Worker**负责耗时的文档解析，结果写回数据库。
- **PostgreSQL**保存文档内容、任务和检索所需的分块。
- **外部模型服务**根据 API 提供的上下文生成回答。

拆出 Worker 的理由，也应该写在图旁边：本例希望上传接口尽快返回，解析在后台完成，前端通过任务状态展示进度。是否值得单独部署 Worker，还要结合文档大小、处理时长和运维成本判断。

一张只写着 React、Python、PostgreSQL 的图，能告诉你用了什么技术，却还不足以解释这些职责。

可以这样问 AI：

```text
请基于这份需求，提出一张应用架构图，供开发者讨论职责划分。
粒度统一为 Web 应用、API 服务、后台任务、数据存储和外部系统。
每个节点写明职责，每条箭头写明交互内容。
说明哪些部分属于本系统，哪些是外部依赖。
图后解释三项关键设计选择，并把尚未确定的选型标为“待定”。
```

如果项目已经存在，把“基于需求提出方案”换成“基于仓库还原当前实现”。这两种任务，需要 AI 提供的证据完全不同。

### 拓扑图：检查“运行时到底怎么连”

现在把上面的方案部署到服务器。Web 页面能打开，但问答一直失败。

你需要检查的是访问链路：浏览器先到哪里？反向代理把请求转给谁？API 能不能访问模型服务？Worker 能不能连上数据库？

![AI 知识库的逻辑连接与部署示意：浏览器经反向代理访问应用主机上的 API；API 和 Worker 连接数据库，API 访问外部模型。](/images/blog/choose-the-right-diagram-for-ai/topology.svg)

拓扑关注节点和连接。在网络领域，拓扑既可以描述物理连接，也可以描述逻辑连接；它不只是“服务器摆在哪里”。[Cisco 对网络拓扑的说明](https://www.cisco.com/site/us/en/learn/topics/networking/what-is-network-topology.html)

在软件项目里，你也可能听到“服务拓扑”或“依赖拓扑”。因此，提需求时要说清：节点代表机器、进程、服务实例，还是逻辑模块？线代表网络可达、实际调用，还是依赖？

本例画的是简化的逻辑连接与部署示意。它没有表达防火墙、访问控制或高可用配置，不能据此判断部署是否安全、是否具备容灾能力。

可以这样问 AI：

```text
请根据部署配置，画一张当前测试环境的服务连接拓扑图，用于排查连通性。
标出浏览器、反向代理、API、Worker、数据库和外部服务。
按主机或运行环境分组，连线表示连接发起方 → 目标服务。
在有配置依据时标注协议和端口；无法确认的连接单独列为待核实。
不要把期望部署方案混进当前环境。
```

注意：API 能连到数据库，不等于某次请求一定成功。连接、权限、数据和业务逻辑，仍要分别核实。

### 流程图：追踪“一件事如何完成”

如果问题变成“用户上传文档后，系统具体做了什么”，就应该沿着一次操作往下追。

![文档上传处理流程图：API 保存任务后返回任务 ID，Worker 异步领取并解析，根据处理结果进入可检索或失败状态。](/images/blog/choose-the-right-diagram-for-ai/flow.svg)

这张图只看“上传到可检索”这一段：API 接收上传并保存任务，返回任务 ID；Worker 异步领取任务、解析文档、写入分块；处理成功后标记可检索，失败则记录错误并展示失败状态。响应返回和 Worker 开始执行没有严格的先后保证，图中的分支表达的是任务依赖。

这里最值得检查的往往是分支：不支持的文件怎么办？解析失败后在哪里结束？是否允许重试？用户看到“上传成功”，指文件接收完成，还是已经可以检索？

图中省略了文件校验和重试细节。到了实现阶段，可以把这些分支继续展开。

可以这样问 AI：

```text
请画出“用户上传文档 → 文档可以被检索”的业务流程图。
明确起点、终点、判断条件和失败出口。
区分 API 同步返回与 Worker 后台处理，在步骤上标注执行者。
覆盖文件校验失败、解析失败和成功三条路径。
重试策略尚未确定，请作为待决策问题列出，不要自行补成既定逻辑。
```

架构图中的一个系统节点，在流程图里可能对应多个动作。“API 服务”是一个参与者，“保存任务”才是一个步骤。

## 遇到这些问题，可以直接换一种图

这四类图够你建立基本判断，但不必把所有问题都挤进去。

| 你正在问的问题 | 更合适的表达 |
| --- | --- |
| 登录时，前端、后端、认证服务按什么顺序交互？ | 时序图，沿时间展示消息和返回 |
| 一个解析任务能处于哪些状态，什么事件触发变化？ | 状态图，展示状态与迁移条件 |
| 用户、文档、会话、消息之间是一对多还是多对多？ | ER 图，展示实体、关系和基数 |
| 新功能应该放进哪个代码模块？ | 模块结构图或组件图，配合职责说明 |
| 一次失败请求在哪里耗时最长？ | 调用链、日志和耗时数据，再据此补图 |

比如“上传为什么卡住”并不能只凭图名决定。要先确认你是在查网络连接、后台步骤、任务状态，还是具体调用的耗时。

时序图尤其适合多方交互的先后关系，Mermaid 官方也将其描述为展示参与方如何交互以及交互顺序的图。[Mermaid 时序图文档](https://mermaid.js.org/syntax/sequenceDiagram.html)

## 和 AI 交互时，把这六件事交代清楚

选对图，只完成了一半。剩下的一半是限定 AI 可以画什么、画到多细、依据什么来画。

**第一，目的。** “帮助新同事理解模块职责”和“定位上传失败”，会得到不同的取舍。尽量把目的写成一个看完图之后能回答的问题。

**第二，范围。** 当前系统还是目标方案？本地、测试还是生产？整个产品还是一次上传？先固定一个范围，避免几种状态混在一起。

**第三，粒度。** 节点是系统、服务、模块、函数，还是业务动作？优先让主要节点处于可比较的层级。确实需要展开某个服务时，用分组或子图表达包含关系。

**第四，关系。** 每条线到底表示包含、调用、依赖，还是下一步？图里可以出现多种关系，但要用标签或图例区分。不要让读者猜箭头的含义。

**第五，依据。** 给现有仓库画图，要求 AI 先阅读代码和配置，并列出对应文件、入口或配置项；给新项目设计方案，则要求把假设和取舍写出来。没有证据的节点，不能直接当成事实。

**第六，输出形式。** 需要持续修改，就保留图的源码；需要放进博客或文档，再导出目标平台支持的图片格式。要求 Mermaid 时，要确认发布平台能渲染，并实际预览一次。

还有一个细节：**绘图语法和图的用途是两回事。** Mermaid 的 `flowchart` 提供节点、边和分组等能力，可以承载多种方框关系图；使用这种语法，并不意味着你表达的一定是业务流程。[Mermaid flowchart 文档](https://mermaid.js.org/syntax/flowchart.html)

## 一个可以反复使用的提示词模板

如果你不确定该选哪种图，可以把“选择视角”也交给 AI，但把判断依据讲清楚：

```text
我想通过图回答的问题是：[具体问题]。
读者是：[自己 / 新同事 / 开发者 / 运维 / 业务人员]。
范围是：[当前实现或目标方案]，限定在 [环境 / 模块 / 场景]。
可用材料是：[需求文档 / 仓库 / 部署配置 / 日志]。

请先用一句话推荐最合适的图，并说明它能回答什么。
如果一张图需要混入多种难以区分的关系，请拆成两张。

作图前，先列出节点、关系及依据，区分：
1. 材料中已经确认的事实；
2. 你的推断或建议；
3. 缺失的信息。

然后输出图：
- 主要节点保持统一粒度，必要时用分组展开；
- 为连线添加语义标签，多种线型提供图例；
- 不把缺失信息自行补成事实；
- 优先展示回答问题必需的内容，细节另列；
- 保留可编辑源码，并说明如何预览。

最后说明：这张图能支持哪些判断，还有哪些问题需要其他证据。
```

重要项目可以分两轮执行：先让 AI 列节点和关系，你纠正理解，再让它正式画图。一个凭空出现的 Redis，在文字清单里通常比在几十条连线中更容易被发现。

## 拿到图之后，先验收内容

配色和对齐可以最后再调。先看这五项：

1. **问题有没有得到回答？** 想找上传失败的位置，图却只列了技术栈，就需要换视角。
2. **节点和连线有依据吗？** 每一条现状关系，都应该能回到代码、配置、日志或你提供的材料。
3. **状态有没有混淆？** 当前实现、建议改造和待定方案，要能一眼区分。
4. **关系是否准确？** 特别检查同步与异步、包含与调用，以及箭头方向。
5. **关键分支是否完整？** 画流程时检查失败出口，画拓扑时检查外部依赖，画架构时检查职责和边界。

“能渲染”只说明绘图语法过关。图是否可信，还要靠这些检查。

下次 Vibe Coding，不妨先把“帮我画一张架构图”改成一句更具体的话：

> 我想弄清楚用户上传文件后，API 什么时候返回、Worker 什么时候开始，以及失败会在哪里被记录。请基于当前代码，选择能回答这个问题的图。

当问题具体到这个程度，图才开始真正帮你推进项目。
